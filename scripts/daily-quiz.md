# 毎日のクイズ生成手順

前日のAIニュースから、4つの読者層それぞれに1問ずつの4択クイズを作り、サイトに反映する。

作業ディレクトリ: このリポジトリのルート

## 1. 対象日を決める

生成は前夜に走り、**翌日の日付で公開する**。

- 公開日 `PUBLISH_DATE` = 実行時点のJST日付の翌日（例: 7月25日23時に実行 → `2026-07-26`）
- ニュースの対象日 = 実行時点のJST日付（例: `2026-07-25` のニュース）

`data/PUBLISH_DATE.json` がすでに存在する場合は、その日の分は作成済みなので何もせず終了する。

## 2. ニュースを集める

WebSearch で対象日のAI関連ニュースを検索する。以下のような切り口で複数回検索し、4つの層に配分できる題材を探す。

- 対象日のAI業界の主要ニュース全般
- 新しいモデル・製品・機能のリリース
- 企業の買収・資金調達・提携
- 企業のAI活用や市場規模に関する調査・予測

各層に配分する題材の観点:

| 層 | id | 選ぶ題材の観点 |
| --- | --- | --- |
| 学生 | `student` | AIの基礎用語や身近な使われ方。前提知識なしで解ける |
| 一般企業 | `business` | 業務でのAI活用、注意点、市場規模・調査結果 |
| IT企業 | `it` | 製品・サービス動向、業界構造、M&Aや競合関係 |
| IT技術者 | `engineer` | モデル仕様、API、アーキテクチャ、ベンチマーク |

同じニュースを別の層で扱ってもよい（切り口を変える）。ただし問題文・選択肢・解説はそれぞれ独立に書く。

## 3. 著作権のルール

**このセクションは最優先で守る。** 毎日自動で外部に公開するため、一度崩れると気づかないまま侵害を積み上げることになる。

### 絶対にやらないこと

- **記事本文の転載・貼り付けをしない。** 一文単位でもコピーしない
- **記事の文をそのまま翻訳しない。** 翻訳は翻案にあたりうる。英語記事を扱うときが最も危険で、「英文を1文ずつ日本語にする」書き方は禁止
- **画像・図表・スクリーンショット・ロゴを一切使わない。** このサイトは文章のみで構成する。報道写真や企業ロゴの無断使用は最も明確な侵害であり、例外は作らない
- **記事の見出しや文章をクイズの選択肢にしない**（「次のうち実際の見出しはどれか」形式の出題を作らない）
- **有料記事・購読者限定記事を出典にしない。** 内容を要約して外に出す形になる

### 書き方

- 事実（数字・日付・企業名・発表内容）そのものに著作権はない。**保護されるのは表現**。だから「事実だけを取り出し、表現は捨てる」と考える
- **複数の記事から事実を確認し、自分の言葉で構成し直す。** 1本の記事だけを見て書くと、無意識にその記事の論理構成と語順をなぞってしまう
- 書いたあとに**元記事を閉じた状態で読み返し**、元記事の文が透けて見えないか確認する。似ていたら、順序と切り口を変えて書き直す
- 解説には**元記事にない自分の観点**を1つ入れる（読者層にとっての意味、背景の補足など）。これがあると独自の著作物として成立しやすく、読者にとっての価値も上がる
- どうしても原文の表現を出す必要があるときのみ、**全角40文字以内**で鉤括弧に入れ、直後に出典を示す。1問につき1箇所まで。基本は引用せずに済ませる

### 出典表記

- **各問に必ず `source` を付ける。** これは著作権対応であり、同時に信頼性の担保でもある
- `source.title` には**実際の記事見出しをそのまま**書く（媒体名を先頭に付ける）。見出しを改変すると誤帰属になるので変えない
- `source.url` は**検索結果に実際に出てきたURLだけ**を使う。組み立てたり推測したりしない。リンク切れは信頼性を損なう
- アグリゲーターより一次情報・大手メディアを優先する

### 考え方の軸

このサイトの立ち位置は**「記事の代わりに読ませるもの」ではなく「記事へ送り出すもの」**。クイズを解いた人が出典リンクを踏みたくなる状態が正しく、記事を読まなくても内容が全部わかる解説を書いてしまったら、それは行き過ぎ。この線を守れば著作権上も安全側に立てる。

## 4. 作問ルール

- **出典で直接確認できない事実は出題しない。** 推測や「たしかこうだったはず」で問題を作らない
- **裁判・容疑・疑惑など、事実認定が済んでいない話題は避ける。** 「〜と報じられた」形でも出題しない。特定の個人や企業に不利益を与える内容は、名誉毀損の観点からも扱わない
- 誤答の選択肢も、もっともらしく作る（明らかにふざけた選択肢は入れない）
- **実在する企業・製品を誤答の選択肢に使うときは、事実と誤認されない形にする。** 「A社が実際にやっていないこと」を選択肢にするのは、解説で明確に否定される場合のみ
### 題材が足りない日の埋め方

ネタが4層分そろわない日は、次の順で対応する。**無理に薄い問題をひねり出すのが一番よくない。**

1. **問題を層をまたいで使い回す。** 同じ問題を両方の層のキーに同じ内容で書く。フロントエンドが問題文の一致を自動検出し、「この問題は◯◯向けと共通です」と表示するので、生成側で管理することは何もない
2. それでも埋まらない層は**省略する**。フロントエンドは欠けた層のタブを自動的に隠す

使い回してよい組み合わせ（読者の関心が近い順）:

- `business` ⇔ `it` — もっとも自然。企業のAI活用と業界動向は地続き
- `it` ⇔ `engineer` — 製品・技術寄りの話題なら成立する
- `student` ⇔ `business` — 基礎的な話題なら成立する

**`student` と `engineer` の使い回しは避ける。** 求める深さが正反対なので、どちらかにとって無意味な問題になる。この2層が埋まらないときは省略する方がよい。

3層以上で同じ問題を使い回すのも避ける。サイト全体がその日1問だけになり、層を分けている意味が失われる。

分量（通勤・通学中に読める長さを守る）:

- 問題文: 全角120文字以内
- 選択肢: 4つ、各全角40文字以内
- 解説: 全角80〜200文字。「なぜそれが正解か」と「だから何が言えるか」を1〜2文で

### 文体

**「です・ます」体で統一する。** 毎日読まれるサイトなので、日によって文体が変わると同じサイトに見えない。学生も読者に含むため、硬い「だ・である」体は使わない。

- 問題文の結びは「〜でしょう？」
- 解説の結びは「〜です」「〜ます」
- 断定を避けたい推測には「〜でしょう」「〜と見られます」を使う

### 出典の新しさ

**原則として、公開日から4日以内に報じられた話題を使う。** 「昨日のAIニュース」を謳うサイトなので、古い話題が混ざると看板と中身がずれる。

- 理想は公開日の前日〜前々日
- 4日を超える話題を使うのは、それが今も業界の中心にある場合のみ（大型モデルのリリースなど、日次では発生しない題材）。その場合も1日1問までにとどめる
- 新しい話題が足りない層は、古い話題で埋めるより**使い回しか省略**を選ぶ

## 5. ファイルを書く

`data/PUBLISH_DATE.json` を作成する。既存の `data/2026-07-25.json` が形式の見本。

```json
{
  "date": "YYYY-MM-DD",
  "questions": {
    "student": {
      "q": "問題文",
      "choices": ["選択肢1", "選択肢2", "選択肢3", "選択肢4"],
      "answer": 0,
      "explanation": "解説",
      "source": { "title": "媒体名: 記事タイトル", "url": "https://..." }
    },
    "business": { },
    "it": { },
    "engineer": { }
  }
}
```

- `answer` は正解の選択肢の**0始まりのインデックス**
- 省略する層は、キーごと入れない

次に `data/index.json` の**先頭**に1行追加する（新しい順に並べる）。`segments` には実際に作成した層のidだけを書く。

```json
[
  { "date": "YYYY-MM-DD", "segments": ["student", "business", "it", "engineer"] }
]
```

## 6. 検算する

コミット前に必ず確認する。

- `data/PUBLISH_DATE.json` がJSONとしてパースできる
- 各問の `answer` が指すインデックスの選択肢が、解説の内容と一致している（**ここを間違えると正解が入れ替わる**）
- `choices` の要素数が4
- `source.url` が検索結果に実在したURLである
- `index.json` に追加した `segments` が、実際のキーと一致している
- **各解説を元記事と並べて読み比べ、表現が似ていないか確認する**（セクション3の基準）。似ていたら書き直す。ここを飛ばさない

## 7. コミットして反映する

```
git add data/
git commit -m "Add quiz for PUBLISH_DATE"
git push
```

push すると Vercel が自動でデプロイし、公開日の0時（JST）にサイト側の表示が切り替わる。

## 8. X投稿用の文面を用意する

`social/PUBLISH_DATE.txt` に、その日の告知用の文面を書き出す（投稿は手動で行う）。

- **答えと解説は書かない。** サイトに来てもらうのが目的
- 4層のうち1つ（その日いちばん反応が取れそうな層）の**自作の問題文**を載せ、続きはサイトで、という形にする。記事の見出しや本文は載せない
- 140文字程度に収め、末尾に **`https://ai-quiz-three-brown.vercel.app/`** を置く（独自ドメインに移行したらこの行を書き換える）
- ハッシュタグは `#今日のAIクイズ` と、題材に応じて1〜2個まで

## 完了したら

実行結果として以下を報告する。

- 公開日と、作成した層の一覧（省略した層があればその理由）
- 各問の題材と出典媒体
- push が成功したかどうか
