# 日次点検の手順書

`daily-ai-quiz` が生成したその日の分を検品し、サイト全体の健全性とセキュリティを確認して、報告書を残す。

このタスクの原則は **「点検と報告は自律的に、変更は狭い範囲だけ」**。本番サイトは公開されており、変更はレビューなしに即公開される。壊す権限を持たないことが、このタスクの価値を守る。

## 最重要の原則: 仕事を作り出さない

**異常がなければ「異常なし」と1行書いて終わってよい。** 毎日何かを見つけて直さなければならない、と考えないこと。

自律タスクの最大の失敗は、変更する理由がない日に変更してしまうことである。細かな言い換え、好みの違いによる書き換え、根拠のないリファクタリングは**やらない**。動いているものに触らないのが、このサイトを長く保つ唯一の方法である。

改善提案も、出すべきものがなければ**0件でよい**。

## 1. 準備

作業ディレクトリはこのリポジトリのルート（実行するタスク側で指定される）。
公開URL: `https://ai-quiz-three-brown.vercel.app/`

- `scripts/daily-quiz.md` を読む。**そこに書かれたルールが検品の基準**である
- `reports/` の直近3日分を読む。**過去に「判断が必要」として上げた項目や、提案して見送られた項目を再提出しない**

点検対象日 `TARGET` は「実行時点のJST日付の翌日」（`daily-ai-quiz` が直前に作った公開日）。

## 2. 当日の生成物を検品する

`data/TARGET.json` について、以下を機械的に確認する。**目視で済ませずスクリプトで検算すること。**

- JSONとしてパースできる
- **`answer` が指す選択肢が解説の内容と一致している** — ここが狂うと誤答を正解として配信する。最も重大な欠陥
- `choices` が4つ、各全角40文字以内
- 問題文が全角120文字以内、解説が全角80〜200文字
- 文体が「です・ます」で統一されている（文末が です/ます/ました/でした/ません/でしょう）
- 問題文が「〜でしょう？」で終わっている
- `data/index.json` の先頭に `TARGET` があり、`segments` が実際のキーと一致している

### 出典の検証

- **各 `source.url` に実際にアクセスして到達を確認する。** `403` や `429` はbot対策やレート制限であり、リンク切れではない。ブラウザのUser-Agentで再試行するか、ブラウザツールで開いて記事の存在を確かめる。**404や別記事へのリダイレクトは本物の欠陥**
- **出典の日付が公開日から4日以内**か確認する。超えている場合、それが日次では発生しない大型題材（モデルのリリース等）かを見て、1問だけなら許容、複数あれば指摘する

### 著作権の検証

`scripts/daily-quiz.md` のセクション3が基準。

- 各解説を出典記事と読み比べ、**表現・語順・論理構成が元記事をなぞっていないか**確認する。特に英語記事の逐語訳になっていないか
- 鉤括弧が**要約なのに直接引用のように見える**使い方になっていないか
- 引用がある場合、全角40文字以内・1問1箇所以内か
- 画像・図表・ロゴを使っていないか（このサイトは文章のみ）

## 3. 蓄積データの健全性

日が経つほど効いてくる観点。**過去分もまとめて見る。**

- **リンク切れ**: 過去の全 `source.url` を確認する。古い記事は消える。死んだリンクは信頼性を直接損なう
- **題材の重複**: 過去7日と同じニュースを出題していないか。日が経つと起こりやすく、毎日読む人にすぐ気づかれる
- **孤児ファイル**: `data/*.json` と `index.json` の食い違い（どちらかにしかない日付）
- **`social/` の文面**: プレースホルダや未設定URLが残っていないか

## 4. 本番サイトの検証

- `TARGET` のクイズが公開URLで実際に読めるか（デプロイが通っているか）
- **セキュリティヘッダが全て残っているか** — `Content-Security-Policy` / `X-Frame-Options` / `X-Content-Type-Options` / `Referrer-Policy` / `Permissions-Policy`。**消えていたら重大**
- 非公開のはずのパスが404か — `/scripts/daily-quiz.md`、`/README.md`、`/reports/`、`/social/`
- ブラウザで開いてコンソールエラーがないか
- モバイル幅（375px）で横スクロールが発生していないか

## 5. セキュリティ点検

- リポジトリと**コミット履歴全体**にAPIキー・トークン・秘密鍵が混入していないか
- 新しいコミットの author/committer が GitHub の `users.noreply.github.com` 形式のままか（個人のメールアドレスに戻っていないか）。**確認したアドレスを報告書に書かないこと**
- `assets/app.js` の `safeHttpUrl()` が残っており、`source.url` の検証を通してから `href` に入れているか。**この防御が外れると、生成データ経由のXSSが復活する**
- `innerHTML` / `eval` / `document.write` が使われていないか
- 依存パッケージやビルド工程が増えていないか（このサイトは依存ゼロを維持する）

## 6. 直してよいもの / 直してはいけないもの

### 直してよい（狭い範囲）

- 文体の不統一、誤字脱字
- `social/` のプレースホルダや未設定URL
- `index.json` と実ファイルの食い違い
- リンク切れの出典 — 同じ記事の生きたURLが見つかればそれに差し替える。見つからなければ `url` を外し、`title` だけ残して出典表記は維持する

直した場合、**修正内容を報告書に必ず書く**。

### 直してはいけない（報告書に書いて人間の判断を待つ）

- **クイズの正解・選択肢・問題文の変更** — 誤りを見つけても直さず報告する。判断を誤ると誤情報を配信するため、人間が見るべき
- UIの見た目・レイアウト・配色の変更、機能追加
- セキュリティヘッダを緩めること、`safeHttpUrl()` の削除・変更
- `about.html` / `privacy.html` の記載内容の変更（著作権・プライバシーに関わる文面）
- `scripts/daily-quiz.md` の著作権ルールの緩和
- 過去のクイズデータの削除
- `git push --force`、履歴の書き換え、ブランチの削除
- 依存パッケージ・ビルド工程の追加

## 7. 報告書を書く

### 前提: 報告書は全世界に公開される

`reports/` はGitHubの公開リポジトリに入る。`.vercelignore` はWebサイトの配信対象から外すだけで、**GitHub上では誰でも読める。**

したがって報告書は**公開前提で書く。** 以下は絶対に書かない。

- **未修正の脆弱性の具体的な内容・再現手順・該当箇所。** 「どこがどう弱いか」を公開すると、直す前に攻撃の手引きを配ることになる
- **個人情報** — メールアドレス、本名、アカウント名、`C:\Users\...` のようなユーザー名を含むパス
- APIキー・トークン・認証情報（値そのものだけでなく、その存在場所も）

### セキュリティ上の問題を見つけたときの書き方

報告書には**「あることだけ」を書き、詳細はタスクの完了報告で伝える。** 完了報告は本人にしか届かないので、そこが詳細の置き場になる。

```
## 判断が必要なもの
- セキュリティに関する要対応が1件あります（緊急度: 高）。内容は本報告書には記載せず、完了報告で伝えます。
```

修正が完了して公開済みの防御については、詳細を書いてよい（すでに公開されているコードから読み取れるため、隠す意味がない）。

### 形式

```markdown
# 点検報告 TARGET

## 判定
異常なし / 要対応N件

## 検品結果
（正解整合・出典到達・文字数・文体・著作権の各結果を簡潔に。問題なければ1行ずつでよい）

## 直したもの
（なければ「なし」）

## 判断が必要なもの
（直してはいけない種類の問題。なければ「なし」。緊急度がわかるように書く）

## 改善提案
（最大3件。根拠と、やらない場合の影響を1〜2文で。出すものがなければ「なし」）
```

**過去3日の報告書で既に挙げた提案を再掲しない。** 見送られた提案は見送られたものとして扱う。

## 8. コミットする

変更（報告書を含む）があれば commit して push する。

```
git add -A
git commit -m "Daily review TARGET"
git push
```

- **`--force` は使わない。** push が失敗したら、原因を報告書に書いて止める
- 変更が何もなければコミットしない

## 完了したら

以下を報告する。**この完了報告は本人にしか届かないので、報告書に書けなかった詳細はここに書く。**

- 判定（異常なし / 要対応N件）
- 直した内容
- **人間の判断が必要な項目**（あれば最初に、目立つように）
- **セキュリティ上の問題を見つけた場合は、ここに具体的な内容・該当箇所・想定される影響を書く。** 報告書側には「あること」しか書いていないため、ここが唯一の詳細の伝達経路になる
- 改善提案の有無
